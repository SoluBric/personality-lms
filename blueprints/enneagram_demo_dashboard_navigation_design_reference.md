# Enneagram Demo App --- Dashboard & Application Orientation Design Reference

**Document type:** Conceptual blueprint / design reference\
**Intended use:** Lightweight scaffolding and inspiration for Codex
while developing the demo application\
**Scope:** Dashboard, primary navigation and orientation between the
main areas of the demo

------------------------------------------------------------------------

## How to Use This Document

This is intentionally the lightest of the design-reference documents.

The Dashboard does not need to become a major product feature in the
first demo. Its main job is to orient the learner and provide useful
entry points into the richer areas already described in the Profile,
Pathways, Learning and Team blueprints.

This is **not a prescriptive layout or navigation specification**. The
eventual structure, terminology, components and visual treatment remain
open.

------------------------------------------------------------------------

# 1. Overall Application Model

The demo currently has four substantive experience areas:

### Profile

> **How do I tend to operate?**

Assessment results, strongest patterns, all-nine exploration, combined
profile, strengths, challenges, development levels and connections.

### Pathways / Development

> **What could I develop?**

Skills, development opportunities, recommendations, goals, pathways and
progress.

### Learning

> **How can I develop it?**

Courses and other learning experiences placed in their personalised
development context.

### Team

> **How do we tend to operate together?**

Colleagues, relationships, team patterns, shared learning and team
pathways.

The Dashboard sits above these primarily as an orientation and
continuation point.

------------------------------------------------------------------------

# 2. Dashboard Purpose

The Dashboard broadly answers:

> **Where am I, and what might I want to do next?**

For the demo, it can remain compact.

Useful functions might include:

-   reminding the learner of their profile;
-   showing their current development focus;
-   continuing active learning;
-   surfacing a current pathway;
-   providing access to their team;
-   highlighting one useful next action.

It does not need to reproduce all information from the other areas.

------------------------------------------------------------------------

# 3. Possible Dashboard Content

A simple Dashboard might draw from several sources.

## Profile

A compact reminder such as:

**Emily Carter**\
**9 / 2 / 6**

with access to the full Profile.

------------------------------------------------------------------------

## Current Development

A current development focus or pathway.

Example:

**From Accommodation to Constructive Assertion**

or perhaps a current skill such as:

**Assertive Communication**

------------------------------------------------------------------------

## Continue Learning

A course currently in progress.

Example:

**Finding Your Voice**

with simple progress information.

------------------------------------------------------------------------

## Recommended Next

One contextually useful next step.

This might come from:

-   the current pathway;
-   a selected development goal;
-   a profile recommendation;
-   a team need.

------------------------------------------------------------------------

## Team

A compact Team Atlas entry point, perhaps including:

-   team name;
-   number of members;
-   current shared development theme or pathway.

------------------------------------------------------------------------

# 4. Dashboard as a Personalised Launch Point

The Dashboard may feel more useful if it reflects the learner rather
than behaving like a generic LMS home screen.

For example, Emily's Dashboard might naturally foreground:

-   her 9 / 2 / 6 profile;
-   her current assertiveness-related development pathway;
-   a course she is completing;
-   Team Atlas.

James's Dashboard could foreground different development content even
though both users have access to the same application areas and course
catalogue.

The amount of personalisation can remain modest.

------------------------------------------------------------------------

# 5. Possible Navigation Model

The main application navigation could remain very simple.

Conceptually:

**Dashboard**\
**Profile**\
**Pathways**\
**Learning**\
**Team**

These labels are placeholders rather than fixed product terminology.

For example, **Pathways** might eventually become:

-   Development;
-   My Development;
-   Growth;
-   Development Map;
-   another term that better fits the eventual visual language.

Similarly, **Learning** could be:

-   Courses;
-   Learning;
-   Library;
-   another suitable label.

Codex can determine what works most naturally with the wider interface.

------------------------------------------------------------------------

# 6. Navigation Between Concepts

One of the more important ideas is that navigation does not need to
happen only through the primary menu.

The content itself can create meaningful transitions.

Examples:

**Profile insight**\
→ related skill\
→ pathway

**Skill**\
→ contributing course

**Course**\
→ related pathway

**Relationship insight**\
→ shared course

**Team development theme**\
→ team pathway

**Course**\
→ personal + relationship + team contexts

These contextual links can make the application feel like one connected
development system rather than several independent modules.

------------------------------------------------------------------------

# 7. Orientation and Context

Because the same object can appear in several contexts, it may
occasionally be useful to help the learner understand where they are.

For example, **Constructive Conflict** could be reached from:

-   Emily's personal pathway;
-   the Emily ↔ James relationship;
-   Team Atlas's pathway.

The interface may preserve some indication of that context.

This could be achieved through breadcrumbs, contextual labels, pathway
indicators or another mechanism.

No particular solution is required.

------------------------------------------------------------------------

# 8. Cross-Area Continuity

A useful quality for the demo is continuity between the major areas.

For example:

### Profile

> You may delay disagreement in order to preserve harmony.

↓

### Development

> Assertive Communication

↓

### Pathway

> From Accommodation to Constructive Assertion

↓

### Course

> Finding Your Voice

↓

### Team

> This capability may also help in your working relationship with James.

This continuity is more important than having a sophisticated Dashboard.

------------------------------------------------------------------------

# 9. Progress at Application Level

The Dashboard may surface progress, but it should avoid reducing the
learner's overall development to one score.

Potentially useful indicators include:

-   current course progress;
-   pathway progress;
-   courses completed;
-   active development focus;
-   skills currently being developed;
-   team pathway activity.

A single global:

> **Development Score: 74%**

is probably less useful because it implies a precision the system does
not genuinely possess.

------------------------------------------------------------------------

# 10. Possible "Next Step" Logic

The Dashboard could surface one or a few useful next actions.

Examples:

-   Continue **Finding Your Voice**
-   Explore your **Type 3 growth resources**
-   Continue **From Accommodation to Constructive Assertion**
-   Review your working dynamic with **James**
-   Explore Team Atlas's shared pathway

The demo does not require a complex prioritisation algorithm.

The purpose is simply to create a sense that the system understands the
learner's current development context.

------------------------------------------------------------------------

# 11. What the Dashboard Does Not Need

For this stage, there is little need for:

-   extensive analytics;
-   large numbers of widgets;
-   social feeds;
-   notifications infrastructure;
-   certificates;
-   leaderboards;
-   complex activity history;
-   organisational reporting;
-   detailed learning calendars;
-   gamification dashboards.

These could distract from the more distinctive Profile, Pathways and
Team concepts.

# 13. Overall Demo Journey

The application should support free exploration, but a particularly
useful demonstration route remains:

**Dashboard**\
↓\
**Emily's Profile**\
↓\
**Profile insight**\
↓\
**Development skill / pathway**\
↓\
**Course**\
↓\
**Team Atlas**\
↓\
**Emily ↔ James**\
↓\
**Perspective switch**\
↓\
**Shared course**\
↓\
**Team pathway**

This route demonstrates how the same underlying content connects across
the application.

It should not prevent other navigation routes.

------------------------------------------------------------------------

# 14. What Matters Most for the Demo

The highest-value application-orientation ideas are likely to be:

1.  simple access to Profile, Pathways, Learning and Team;
2.  a Dashboard that feels personalised but remains uncluttered;
3.  a clear current development focus;
4.  easy continuation of learning;
5.  contextual links between the main areas;
6.  preservation of context where the same course or skill appears in
    several places;
7.  freedom to explore rather than a forced linear journey.

# 16. Core Experience

At the application level, the learner should broadly feel:

### "I know where I am."

The major areas have understandable purposes.

### "I know what I can do next."

Current learning and development opportunities are easy to find.

### "Everything is connected."

Profile insight, skills, courses, pathways and team development feel
like parts of one system.

### "I can explore."

The application guides without forcing a single route.

------------------------------------------------------------------------

# 17. Scope Reminder

The Dashboard and navigation are deliberately under-specified at this
stage.

They can evolve once the richer Profile, Pathways, Learning and Team
experiences take shape.

For the first demo, **clarity and continuity are more valuable than
dashboard sophistication**.
